# 02 — Целевая архитектура

## Почему не переписывание с нуля

Вы сказали «можно сказать переделывание». Разберём это честно, потому что от ответа зависит всё остальное.

**Аргументы за переписывание** (они реальные): 0 тестов, ролевой доступ не работает, деньги во float, три реализации бухгалтерии, god-файлы.

**Почему это всё равно плохая идея:**

1. **83 592 строки описывают поведение, которого больше нигде нет.** Ни спеки, ни тестов. Каждое `if (job === "accountant")` — это чьё-то бизнес-требование, о котором никто уже не помнит. Переписывание с нуля = переоткрытие всех этих требований через баг-репорты из прода.
2. **Арифметика времени.** ~5 разработчиков на 83k строк. Даже при оптимистичных 200 строк/день/человек на переписывание с нуля — это ~80+ человеко-недель только на паритет функционала, без единой новой фичи. Бизнес столько не ждёт, а параллельно легаси придётся ещё и поддерживать.
3. **Переписывание не чинит главные проблемы.** RBAC-дыра, float в деньгах и отсутствие CI — это не следствия «плохой архитектуры». Это конкретные дефекты, которые чинятся за недели в существующем коде. Новый проект без CI и с деньгами во float получится ровно таким же — те же люди, те же привычки.
4. **Фундамент не гнилой.** FSD выбрана верно, стек современный, средний файл 85 строк, деньги не протекли в `shared/`. Переписывать нечего — надо доделать то, что начато.

**Что делаем вместо: strangler fig.** Обкладываем систему границами, режем по домену, переделываем модуль за модулем, каждый — под тестами, прод не останавливается. «Переделывание» происходит, но по частям и с работающим приложением на каждом шаге.

**Где переписывание всё же уместно** — точечно, там, где легаси дешевле выбросить, чем чинить:
- `pages/accountingPage` (4 529 строк) → консолидация в одну реализацию (FIN-06)
- `shared/api/base.js` → новый HTTP-клиент (CORE-02)
- Роутер-гарды → переписать с нуля, там 90% кода закомментировано (CORE-01)

## Главная идея: деньги — вертикальный срез с публичным API

Сейчас деньги размазаны по 266 файлам во всех слоях. Просто «отдать команде FIN список папок» недостаточно: профиль ученика (CORE) показывает платежи (FIN), дашборд директора (CORE) содержит вкладку «Moliyaviy statistika» (FIN), список групп (CORE) показывает скидки (FIN). Если не решить это архитектурно, две команды будут постоянно лезть в файлы друг друга и план развалится на второй неделе.

**Решение — денежный модуль с единственной точкой входа и слотами:**

```
src/entities/finance/
├── index.js                    ← ЕДИНСТВЕННЫЙ разрешённый импорт для CORE
├── api/                        ← финансовые эндпоинты, типы, контракты
├── model/                      ← слайсы, санки, селекторы денег
├── lib/
│   └── money/                  ← money kernel (см. ниже)
├── ui/
│   ├── slots/                  ← публичные компоненты для встраивания в CORE
│   │   ├── StudentPaymentPanel.jsx
│   │   ├── FinanceStatsTab.jsx
│   │   └── DebtBadge.jsx
│   └── internal/               ← внутренности, CORE их не видит
└── routes.jsx                  ← FIN сам регистрирует свои роуты и пункты меню
```

`index.js` экспортирует только слоты, `formatMoney` и типы. Всё остальное — приватное.

**Контракт слотов.** CORE встраивает денежный UI как чёрный ящик:

```jsx
// pages/profilePage — владеет CORE
import { StudentPaymentPanel } from "entities/finance";

<Tabs>
  <Tab name="Ma'lumot"><StudentInfo id={id} /></Tab>
  <Tab name="To'lovlar"><StudentPaymentPanel studentId={id} /></Tab>
</Tabs>
```

CORE передаёт `studentId` и не знает ничего про платежи: ни про эндпоинты, ни про расчёт долга, ни про скидки. FIN меняет внутренности слота, не трогая профиль ученика. **Ноль конфликтов.**

Это же решает и дашборд: `directorDashboardPage` остаётся у CORE как оболочка с вкладками, а содержимое «Moliyaviy statistika» — слот `<FinanceStatsTab />` от FIN.

**Правило в одну строку:**
> CORE может **показать** денежное число, полученное готовым, через `formatMoney`. CORE **никогда** не складывает, не умножает и не отправляет деньги.

## Money kernel: конец плавающей точке

Отдельный модуль, владелец — FIN, единственный источник денежной арифметики в проекте.

```js
// entities/finance/lib/money — публичен через shared для форматирования
sum(items, selector)      // безопасное суммирование, никаких reduce+parseFloat
add(a, b) / sub(a, b)
percent(money, rate)      // скидки, ставки — с явным правилом округления
formatMoney(money)        // ЕДИНСТВЕННЫЙ форматтер на проект
parseMoney(apiValue)      // граница: из ответа API в Money
```

**Принципы:**

1. **Никакой плавающей точки.** Внутри — целые минорные единицы (или decimal-строки, см. решение ниже). `parseFloat` для денег запрещён линтером.
2. **Округление — явное и одно.** Сейчас 31 `toFixed()` округляет как попало и в разных местах. Должно быть одно правило, принятое осознанно и записанное в коде.
3. **Граница парсинга одна.** `parseMoney` вызывается на входе из API — дальше по коду ходит только `Money`, а не сырое число.
4. **Форматтер один.** Сейчас `toLocaleString` разбросан по 10+ файлам, каждый со своими опциями. Итог: одна и та же сумма выглядит по-разному на разных экранах.

**⚠️ Решение, которое надо принять с бэкендом (блокирует FIN-02):** в каком виде API отдаёт деньги — число (`12345.67`) или строка (`"12345.67"`)? Если число — точность уже потеряна на сериализации JSON, и это надо чинить на бэкенде, иначе money kernel лечит симптом. Целевое состояние: строка-decimal или целые минорные единицы.

## Настоящий ролевой доступ

Сейчас: 87 роутов, 0 защищённых, `RequirePermission` возвращает `undefined`, роль читается из `localStorage` в 35 местах.

**Целевое:**

1. **Роль — из токена, не из `localStorage`.** `jwt-decode` уже в зависимостях. `localStorage.getItem("job")` подделывается в devtools за пять секунд; подпись JWT — нет. Единый `useSession()` вместо 35 прямых чтений.
2. **Гейтинг на уровне роута, декларативно.** Поле `roles` в конфиге роутов **должно читаться** (сейчас объявлено в 7 местах из 87 и игнорируется):
   ```jsx
   { path: getAccounting(":id"), element: <AccountingPage />, roles: [ROLES.director, ROLES.main_director, ROLES.admin, ROLES.programmer] }
   ```
   Нет роли → редирект на 403, а не пустой рендер.
3. **`<Can>` для элементов внутри страниц** — вместо `{job === "accountant" ? "" : <Button/>}`, которого по коду россыпь.
4. **Источник истины — [`docs/roles/`](../roles/README.md).** Матрица доступа там уже есть. Задача — заставить код ей соответствовать, а не изобретать заново.

**И главное:** фронтовый гейтинг — это UX, а не безопасность. Он прячет кнопки, но не защищает данные. **Реальная защита — только на бэкенде**, и это надо подтвердить (см. [README](./README.md#что-надо-решить-до-старта)).

## Границы, которые проверяет линтер

Договорённости, которые не проверяются автоматически, живут до первого дедлайна. Поэтому — `eslint-plugin-boundaries`:

```js
// ЗАПРЕЩЕНО — импорт внутренностей чужого домена
import { paymentSlice } from "entities/finance/model/paymentSlice";
import Table from "entities/accounting/ui/acauntingTables/...";

// РАЗРЕШЕНО — только публичный API
import { StudentPaymentPanel, formatMoney } from "entities/finance";
```

Плюс правила: `parseFloat` на денежных переменных, ручной `toLocaleString` для денег, прямой `localStorage.getItem("job")` — ошибка линтера с внятным текстом «используй X».

Это то, что превращает разделение команд из джентльменского соглашения в свойство репозитория.

## Модульные роуты и меню

По churn за 6 месяцев `widgets/menuBar` (38 коммитов) и `app/routers` (35) — самые горячие точки проекта. Оба — единые файлы на весь проект. Две команды в них будут конфликтовать постоянно.

**Было:** один `routersConfigList.jsx` на 44 роута + один `menuConfig.js` на всё меню.

**Стало:** каждый домен объявляет своё у себя, ядро собирает:

```js
// app/routers/config/index.js — собирает, но не содержит
import { financeRoutes } from "entities/finance/routes";
import { educationRoutes } from "entities/education/routes";

export const routes = [...financeRoutes, ...educationRoutes];
```

FIN добавляет финансовую страницу → правит только `entities/finance/routes.jsx`. Конфликтов с CORE нет физически.

## Инфраструктура

| Что | Сейчас | Целевое |
|-----|--------|---------|
| HTTP | `useHttp` в 224 файлах, без интерсепторов | Один клиент: auth-заголовки, refresh по 401, нормализация ошибок |
| Server state | 104 слайса + 104 `createAsyncThunk` | RTK Query (уже в зависимостях) — новый код только на нём |
| Типы | нет | TS постепенно: money kernel и API-контракты первыми |
| Тесты | 0 | Vitest + RTL; Playwright на денежные сценарии |
| CI | только деплой | lint + typecheck + tests на PR, master защищён |

**Про TypeScript — важная оговорка:** миграция 980 файлов на TS не является целью этого плана и в него не влезет. Цель — типизировать то, где типы окупаются немедленно: **money kernel и контракты финансовых API**. Остальное — по мере касания. `vite-tsconfig-paths` в devDeps уже есть, инфраструктура готова.
